# Orientation — 先导讲解：先建立共同语言，再开始追问

本文件定义 **Phase 0（先导讲解）**。它是新工作区的默认开场，也是用户随时可以退回的一层。

## 为什么存在

苏格拉底式追问的前提是用户已经站在对象的**内部**。对着一个完全不知道对象形态的人提"你来走一遍主流程"，得到的不是诊断，而是噪音——用户只会说"我不知道"，而下钻到"这个系统由哪些部分组成"这种前置，等于把背景知识拆成几十轮猜谜。

所以顺序是：**先导讲解 → 追问**，不是"追问 → 缺什么补什么"。

## 铁律

1. **新工作区第一次交互，禁止先提问。** 先给先导讲解，讲完再问。不要用"我先问一个热身问题"开场。
2. **先导讲解不是掌握证据。** 讲得再清楚，也不能写 mastery evidence，不能改变节点状态。
3. **讲解期间不提问、不测验。** 不要把讲解写成"边讲边考"，也不要在段末附一道题。
4. **用户随时可以回到这一层。** 任何时刻说"再讲一点 / 我还是不懂这个背景"，就继续讲，不进入提问。

## 触发条件

满足任一条件就执行先导讲解：

- 新工作区首次进入（`init` 之后、第一个 `ask` 之前）——**默认行为，无需用户要求**；
- 用户说"先讲一下 / 给我背景 / 我不了解这个领域 / 先告诉我这是什么 / 别上来就问我"；
- 连续 `--idk`，且缺失的不是单个概念而是整块背景；
- 用户明确表达挫败感（"都说我没了解了"）——这通常说明前面已经跳过先导讲解。

## 讲解清单

按对象实际情况取舍，但**前四项必须覆盖**：

1. **一句话定位 + 真实痛点** —— 这东西是什么，谁在什么场景下被什么流程折磨。
2. **参与者与各自诉求** —— 一张角色表：谁、想要什么、被什么约束。
3. **端到端主流程** —— 编号步骤，每步写清：谁做、系统做什么、产生/改变了什么状态。
4. **术语表** —— 共同语言，最重要的一块。把对象里的黑话逐个用一句话钉死。
5. **关键规则与数字** —— 公式、阈值、上限、口径，以及它们为什么是这个值。
6. **系统是怎么搭起来的** —— 用非程序员能懂的比喻讲分层与数据流向：数据从哪进、经过谁、落到哪。
7. **反直觉设计与常见误解** —— 看起来多余的限制背后通常有真实原因，这是后续追问的富矿。
8. **明确的边界** —— 这个系统刻意**不**做什么。

## 零基础用户：先补一层技术名词

如果用户表示不懂编程（"代码我一窍不通""不懂 FastAPI / Vue"），那么讲解清单第 6 项「系统是怎么搭起来的」**绝不能直接甩框架名、模块名、目录名**。先补一层名词卡，全部用生活类比，并且**先讲它解决什么问题，再讲它叫什么名字**：

| 名词 | 先用大白话说什么 |
|---|---|
| 代码 / 程序 | 写给电脑的一步一步的指令，像菜谱 |
| 前端 | 你看得见、点得到的部分 |
| 后端 | 你看不见、在服务器上干活的部分 |
| 框架（FastAPI / Vue） | 别人搭好的半成品脚手架，省得从零盖房子 |
| 接口 / API | 前后端之间的点菜窗口；前端不能直接翻账本 |
| 数据库 | 能被程序飞快查询的文件柜 |
| ORM | 把"程序里的对象"翻译成"数据库语言"的翻译官 |
| 编程语言（Python / TypeScript） | 写上面这些东西用的人工语言 |

规则：

- **名字后置**：不要在用户还不知道它是什么的时候成串抛名字。出现一个名词，就先给它一个"这东西是干嘛的"。
- 单次讲解引入的新名词**不超过 8 个**；超过就先讲一半，剩下的等用户消化。
- 技术层讲完必须**回到业务**：用"点一下按钮之后发生了什么"把名词串成一条线。
- 用项目里的**真实例子**解释名词，不要用教科书例子。
- 用户说"这个我还是不懂"，就是回到这一层继续讲——**这一层永远不许转去提问**。
- 强调一遍：学会一个项目 ≠ 学会写代码。目标是能说清"数据从哪来、经过谁、到哪去、出错会怎样"。

### 基线必须落地成结构，不能只写备注

探测到基线（会写代码吗？用过这个对象吗？）之后，**必须在 `init` 之后立刻把它变成树上的东西**：

1. **建 blocking 节点**：`node add --blocking`，例如「技术名词层：前端、后端、接口、数据库分别是什么」。
   **只写 `--note` 不算数**——备注不出现在 `render` 里，用户看不见，之后也不再约束任何决策，等于没记。
2. **改写种子措辞**：默认种子是"给程序员看的"（架构与模块划分、接口与契约、依赖与配置……），对零基础用户就是噪音。用 `node update --name` 改成学习者能懂的话。
3. **根节点记原文出处**：谁、什么时候、怎么说的。基线是**用户自述事实**，不是推断。
4. **基线变了要跟着改**：用户从"完全不懂"到"看得懂一点"，节点措辞和提问方式都要更新，不要沿用旧假设。

> ⚠️ 改名的技术风险：`evidence.json` 与 `questions.jsonl` 以**节点名为键**，`state.json` 的 `return_stack` 也按名字引用节点。改名之前先确认该节点没有证据、不在下钻栈里；否则先备份状态目录，改完立刻跑 `validate` + `doctor`。

## 篇幅

"一大堆"是刻意的要求：**宁可一次给足，也不要挤牙膏。**

| 对象规模 | 目标篇幅 |
|---|---|
| 单一概念 / 小工具 | ≥ 800 字 |
| 中型项目、论文、方案 | 1500–3000 字 |
| 大型对象 | 拆 2–3 段连续讲完，**期间不提问** |

因为怕长而删减背景，是本手册允许的最严重错误之一。允许信息过载，不允许信息饥饿。

## 质量约束

- 事实必须来自实际读过的材料，并用 `source add --ref ...` 登记；区分 `project_fact`、`domain_knowledge`、`inference`。
- 不编造 API、公式、参数、行号、项目行为。不确定就写"这一点我还没核实"。
- **不要把 Seed Tree 当教学大纲倾倒。** 讲解讲的是对象的真实结构，不是"我准备考你哪些点"。
- 不复述原始文档。要**解释**，要建立因果：为什么这样、不这样会怎样。

## 讲完之后

1. 用**一行**说明接下来会问哪几类问题——只给方向，不给答案大纲、不给题目。
2. 然后**只问一个问题**，进入正常主循环。
3. 如果用户说"再讲一段 / 还有呢"，继续讲，仍然不提问。

## 与状态机的关系

先导讲解不改变 `scripts/mi.py` 的协议，只是重新排列动作顺序：

```bash
# 1. init（照常）
# 2. source add（登记本次讲解依据的材料）
# 3. 给用户完整讲解 —— 此处不调用 ask
# 4. ask（第一问），此后进入每轮主循环
```

- 讲解时若存在 pending question（例如从旧流程切过来），用 `answer --neutral` 消费它，**不要伪造证据**，也不要为了凑流程硬答。
- 讲解不消耗下钻预算，也不进 `return_stack`；但如果它取代了一次下钻，回来之后仍要按 `--reprobe-of` 重问被中断的能力点。
