# Harvest — 每轮信息沉淀

**规则：用户说过的每一句话，都必须有一个明确的去处。不接受"我记住了"。**

"我记住了"等于没记：它不进树、不进证据、不进来源，跨轮次就蒸发，跨会话就归零。用户被迫重复自己说过的话，是这套机制最严重的事故。

## 触发时机

- **每一轮用户输入之后、决定任何动作之前。** 包括：回答、元指令、抱怨、闲聊、提问、贴材料、只说"嗯"。
- 特别地：用户**抱怨**（"我都说了……你怎么没加进去"）时，先回头把最近几轮重新过一遍，通常能捞出多条早就该落位的信息。

## 六类信息与它们的去处

把这一轮的话逐句过一遍，每一句先归类，再落位：

| 类型 | 典型说法 | 必须落到哪 |
|---|---|---|
| **P 偏好 / 流程要求** | "先讲再问我"、"别用术语"、"别一次问那么多" | **偏好节点**（见下），必须出现在 `render` 里 |
| **B 基线 / 已知** | "我不懂编程"、"我用过这个系统"、"我学过统计" | 能力节点或 blocking 前置；根节点记原文出处 |
| **F 对象事实** | "我们院是按行政班折算的"、"这个字段是审核意见" | `source add`（若来自文件）+ 节点 `--note`（若来自用户口述） |
| **Q 疑问 / 好奇点** | "树放哪了？"、"多少行代码？" | **建节点**；答完把该节点标成对应状态，不要答完就丢 |
| **A 回答 / 证据** | 对 pending question 的回应 | `answer --evidence/--idk/--misconception/--neutral` |
| **S 情绪信号** | "你怎么没加进去"、"我还是不懂" | 触发讲解层回退（`references/orientation.md`），并检查信息是否漏落位 |

一条信息可能有多个面（既是偏好又是基线）——**选一个主去处**，其余用 `--note` 挂靠，不要建重复节点。

## 偏好节点怎么建

偏好不是"待掌握的能力"，不该被提问，但**必须可见**：

```bash
mi.py ... node add --name "教学偏好：先给完整讲解，再开始追问" \
  --parent root --kind practice --origin manual --importance 5 \
  --desc "用户明确要求。影响提问节奏与讲解长度，不是学习目标。" \
  --note "原文与时间：2026-09-30「你应该先用一大堆东西让我初步了解，再去问我问题」"

# 第二步：单独标 deferred —— node add 的 --status 不生效，必须补这一刀
mi.py ... node update --id "教学偏好：先给完整讲解，再开始追问" --status deferred
```

关键点：

- **必须两步走**：先 `node add` 建节点，再 `node update --id <节点> --status deferred` 补一刀。
  ⚠️ **`node add --status deferred` 不生效**（实测：`manual_status` 仍为空，节点保持 `unexplored`，照样进提问队列——AI 会去问用户"请解释项目只读约束"这种荒谬问题）。也可以直接用 `skip --node X`。
- **建完必须验证两件事**：① 回读 `tree.json` 确认 `manual_status == "deferred"`；② 跑 `next` 确认它没进候选。
  "写了参数"和"参数生效"是两回事——**凡是声明引擎行为，先回读状态或查源码，不许凭推测写进文档**。
- `--parent root`：偏好约束全局，不要挂到某个领域节点下面。
- **绝不写 mastery evidence**：偏好被记录 ≠ 用户掌握了什么。
- 偏好被推翻时（用户改主意），更新同一个节点，不要新建一个相反的节点。

## 完整性自检

### 每轮 60 秒自检（`next` 之前）

问自己三句：

1. 这一轮用户说的话里，**有没有哪一句的信息还没有去处**？
2. 新得到的信息，**会不会让某个已有节点的措辞或状态过时**？
3. 用户这个问题，**树上有没有对应的节点**来接住它？没有就建一个。

### 阶段性完整审计（每 5 轮左右，或用户问"树完整吗 / 进度如何"）

1. `questions.jsonl` + `history.jsonl` 全部读一遍；
2. `render` 出当前树；
3. **逐条比对**，找出"用户说过、但树上找不到"的主题；
4. 补建节点或来源，然后 `validate` + `doctor`。

**完整性判据（可验证，不靠感觉）**：

> 用户说过的每一个"我不知道 / 我想知道 / 我是这样用的 / 我希望你怎么教"，都能在 `render` 的输出或 `sources.json` 里找到对应条目。

## 禁止事项

- **不要把提问当掌握。** 用户问"多少行代码"不等于他掌握了代码规模；答案要落到节点，但状态不能因"问过"而升级。
- **不要为了树好看而添加用户没提过、对象里也不存在的领域。** 完整性指的是"信息不丢"，不是"节点越多越好"。
- **不要用 `--note` 代替节点。** 备注不出现在 `render` 里，用户看不见，也不参与 `next` 打分——这正是"等于没记"的典型形态。
- **不要重复建节点。** 同类信息先检索树上有没有既有节点，优先 `node update`。
- **不要伪造来源。** 用户口述记为"用户自述（时间）"，文件事实记为 `source add`，两者不能混。
